# NINA の UDP と TLS

現状、NINA-W102 のファームウェア 3.0.2 を SPI で使用し、Zephyr の IPv4 TCP・UDP
ソケットをオフロードしている。TLS は未対応。

## UDP

2026-11-11 に、TCP クライアントと UDP を従来の種類別命令から 3.0.2 の BSD ソケット
相当の命令（socket / bind / connect / send / recv / sendto / recvfrom / poll など）へ
移行した。各命令は NINA 内の lwIP ソケットを 1 回呼ぶだけで、ソケット同士は独立して
いる。従来の命令で 1.4.8 のときに確認した「TCP に未読データがあると UDP の読み取りが
保留される」制限と、それに伴う同時利用の拒否はなくなった。

命令は NINA の SPI ハンドラー内で実行されるため、ブロックする呼び出しは Wi-Fi 管理を
含む全体を止める。ソケットは作成直後に非ブロッキングにし、接続完了・受信・送信可能の
待ちはドライバー側で poll 命令を繰り返す。非ブロッキングの失敗と「0 バイト」は応答で
区別できないので、受信は先に poll で読めることを確かめ、TCP 送信で 0 が返ったときは
poll のエラーフラグで切断を判定する。接続の成否は SO_ERROR で確認する。
送受信サイズは 1 データグラム 512 バイトに制限し、収まらない受信分は lwIP が捨てる。

## TLS / MQTTS

ファームウェア 1.4.8 の通常の TLS クライアントは NINA 上で TLS を処理し、
NINA の証明書パーティションの CA を使う。ホスト名指定時はその名前を TLS に
渡す一方、IP アドレス指定時はホスト名を設定しない。したがって、単に現在の
IP アドレス指定の TCP 接続を TLS モードに変えるだけでは、接続先の名前を
検証できない。信頼する CA の管理と、ホスト名・時刻の扱いを含めて実装する。

NINA ファームウェアには ATECC を使う別の BearSSL 経路もあるが、このボードでの
配線、設定済みの鍵と証明書、IMU との I2C 共存は未確認。Security チップの利用は
TLS 自体の必須条件ではない。鍵の書き込みやロックは確認作業に含めない。

Zephyr 側の TLS を NINA の TCP ソケットで動かし、テスト用乱数と一時的な
証明書を使って MQTT の接続と送信を実機で確認した。ホスト名の不一致、有効期限
切れ、信頼されない CA のケースでは接続が失敗した。この検証には安全でない
テスト用乱数を使用しており、本番用 TLS の実装完了を意味しない。

本番用には信頼できる暗号用乱数源と CA の管理が必要。ATECC608A は実機で設定と
データの両方が未ロックで、Random コマンドの 2 回の応答が同一だった。この状態の
出力を暗号用乱数として使用しない。将来のクライアント証明書の要否は未定のため、
不可逆な設定やロックは行わない。IMU と共用する I2C バスの速度と排他制御も、
ATECC を使う場合には検討が必要。

別の候補は NINA 内の ESP32 のハードウェア乱数だが、現在の NINA ファームウェア
1.4.8 の SPI コマンドには乱数取得がない。Wi-Fi の RF が有効な状態では ESP32 の
乱数生成器に物理エントロピーが供給されるため、独自ファームウェアで SPI 経由に
公開する方法を検討できる。接続状態と乱数取得失敗の扱い、ファームウェアのビルド、
更新・復旧方法を検証する必要があり、現在は未実装。乱数源が利用できない場合は
TLS の接続を失敗させ、テスト用や非暗号用の乱数にフォールバックさせない。

時刻は Wi-Fi 接続後に SNTP で取得する。ただし通常の SNTP 応答は認証されないため、
TLS 証明書の有効期限を安全に検証するには時刻源の信頼性も別途考慮する。現行の
NINA ファームウェアの TLS 設定では証明書の日付検証が有効になっていないため、
NINA 側の標準 TLS に切り替えるだけでも要件を満たせない。
