# NINA を使った Telnet シェルの調査

Zephyr 4.5.0 の `CONFIG_SHELL_BACKEND_TELNET` を利用するため、NINA 3.0.2 の
低レベルソケットを使う TCP サーバーと混在 `poll` の実装を追加した。実機では
基本コマンド、繰り返しの接続、Wi-Fi 再接続、起動時 SNTP、短時間の IMU FIFO
取得を確認した。一度発生した接続タイムアウトは再起動で回復したが原因は未確定。
長時間動作と MQTT クライアントとの同時利用は未検証。

## 確認した制約

- 従来のドライバーは TCP の `bind`、`listen`、`accept` を実装していなかった。
- Zephyr のソケットサービスは内部の eventfd と Telnet のソケットを同じ
  `poll` に渡す。従来の NINA の `poll` は別種の fd を拒否していた。
- 使用実績のある NINA ファームウェア 1.4.8 の `availDataTcp` はサーバーの
  `available()` を使う。データを送っていない接続を通常の `accept` と同様に
  検出できるとは限らない。またサーバー停止コマンドがない。
- サーバーの常時待ち受けは TCP ソケットを占有する。現行ドライバーは TCP と
  UDP の同時使用を拒否するため、起動時の SNTP にも影響する。
- Zephyr の Telnet バックエンドは認証も暗号化も行わず、フルシェルを公開する。

Arduino の新しい NINA ファームウェアには、接続を受け付ける `accept` と
サーバー停止の実装が追加されている。導入するバージョンと既存の Wi-Fi、TCP、
UDP 動作との互換性を確認した上で、NINA ファームウェアを更新する案がある。
実機の NINA ファームウェア更新は RP2040 アプリの更新とは別の作業である。

## 役割分担と候補

現在の Wi-Fi インターフェースはソケットオフロードで、NINA のファームウェアが
Wi-Fi と TCP/IP を処理し、RP2040 側は SPI コマンドでソケットを操作する。
標準 Telnet バックエンドを使う場合、TCP の待ち受けと送受信は NINA、Telnet
処理と Zephyr シェル、コマンド実行は RP2040 が担当する。NINA に独自の Telnet
アプリケーションを追加する必要はない。

1. **NINA 1.4.8 の既存サーバーコマンドを使う。** ファームウェア更新は不要。
   ただし受信データがあるクライアントの発見を通常の `accept` の代わりに使う
   制約があり、クライアントが先に何か送らないとプロンプトを出せない可能性が
   ある。停止コマンドもない。リスナーの close、再起動、切断後の再生成や
   ソケット ID 再利用をどのように安全に扱えるかは未解決。
2. **NINA 1.5.0 以降の BSD 風ソケットコマンドを使う。** 1.5.0 のソースには
   `socket`、`bind`、`listen`、`accept`、`close`、`poll` などがある。これらは
   既存の Arduino 系クライアントコマンドとは別のコマンド群であり、RP2040 側に
   プロトコルと fd の実装が必要。標準的な接続直後の受け付けと停止に適した候補
   だが、確認した 1.5.0、1.6.0、3.0.1、3.0.2 の `socket_poll` には例外 fd セットを
   初期化していない箇所があり、そのまま信頼できない。修正済みファームウェアを
   用いるか別の方法を検討する必要がある。採用するバージョンは未決定。
3. **Wi-Fi ファームウェアとホスト側ドライバーを変更し、RP2040 のネットワーク
   スタックを使う。** TCP も RP2040 側で処理できる設計だが、現行 NINA の SPI
   ソケットプロトコルを使う小さな変更では済まない。対応する L2 フレーム転送と
   Wi-Fi 制御の仕組みを別途用意する必要がある。

候補 2 を優先調査する。NINA の低レベルソケット API を全通信へ適用するか、
既存 API と併用するかは、ソケット数・識別子・共有状態と TCP/UDP 共存の検証後に
決める。API の存在だけから、既存の UDP 問題が解決すると仮定しない。

## 実装時に解決する点

- `SHELL_BACKEND_TELNET` は `NET_TCP` に依存する。現行ビルドでは `NET_TCP` は
  無効なので、オフロードとの併用時の Kconfig とコードサイズを確認する。
- NINA 通信は単一の mutex を共有する。接続待ちや受信待ちを NINA のブロッキング
  呼び出しに任せると、Wi-Fi 管理や MQTT まで待たせる恐れがある。非ブロッキング
  設定、短い `poll` と停止・キャンセルを確認する。
- 標準 Telnet のソケットサービスが使う eventfd を混在 `poll` で扱い、登録変更を
  遅延なく反映させる。異なるオフロード実装の fd を混ぜるケースは別途定義する。
- 応答形式には複数パラメーターを含むコマンドがある。既存の `nina_request` は
  応答数をコマンドごとに扱っており、`accept` の IP・ポートを含め検証する。
- 再接続、異常切断、リスナーの破棄と再生成、空き fd がない場合の資源回収を
  確認する。ファームウェアの更新前後で Wi-Fi・DNS・SNTP・既存 TCP および MQTT
  の回帰試験を行う。IMU 取得中の SPI 通信負荷と FIFO の欠落も測定する。
